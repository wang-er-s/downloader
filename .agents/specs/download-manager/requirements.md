# 需求文档

## 简介

为 Android、macOS 和 Windows 提供一个可实际使用的下载管理器，并以可行性验证为前提争取同时提供 iOS 版本。界面与主要交互参考 `docs/` 中的截图，并适配移动端和桌面端。用户可以创建和管理 HTTP/HTTPS 下载任务、保存可重复使用的下载配置、选择文件保存位置。后台执行、目录访问和文件打开遵循各平台能力与限制。首期不支持代理、分享、需要认证的资源、磁力链接或视频解析。

## 平台范围与已确认规则

- 必需平台：Android、macOS、Windows；不能以仅 Android 的实现作为首期交付。
- 期望平台：iOS，希望一并提供；必须先验证下载、暂停继续、后台生命周期及文件访问，不能未经确认静默削减功能。
- 通用业务行为以本文为准，平台只负责必要的后台执行、目录授权和系统打开适配；具体最低系统版本在跨平台设计中确认。
- 跨平台范围及 iOS 后台例外已获用户确认：允许 iOS 系统继续管理已提交的后台下载，即使应用进程被系统终止；应用启动时关联系统既有任务并同步状态，不主动重新提交失败或取消的任务。用户在多任务界面主动强制退出时，按系统取消后台传输的行为处理，再次打开应用后恢复记录，等待用户操作。
- 桌面端的最小化、窗口关闭、应用退出和系统休眠需在设计中分别说明，不预设增加托盘、开机自启、后台守护进程或跨设备同步。

## 需求列表

### 需求 1：创建和查看下载任务

**用户故事：** 作为下载管理器用户，我希望通过 HTTP/HTTPS 链接创建下载，并查看下载状态，以便管理文件下载。

#### 验收标准

1. 当用户提交有效的 HTTP/HTTPS 链接时，系统应创建下载任务并开始下载；系统应支持 HTTP 重定向。
2. 如果用户提交空值或格式无效的链接，系统应提示链接无效且不创建任务。
3. 当下载任务进行中时，系统应展示文件名、已下载大小、总大小、完成百分比、下载速度、预计剩余时间和进度指示。
4. 当任务总大小或剩余时间暂不可确定时，系统应以不误导用户的方式展示未知状态，不显示虚构数值。
5. 当下载列表有任务时，系统应显示“下载中”“已完成”“缓存”分类及各自数量，并允许用户切换分类。
6. 系统不应将需要登录认证的资源、磁力链接或视频解析作为首期支持范围。

### 需求 2：暂停、取消和删除任务

**用户故事：** 作为下载管理器用户，我希望控制下载任务并分别管理下载记录和文件，以便安全地中断或清理下载。

#### 验收标准

1. 当用户暂停一个正在下载的任务时，系统应停止该任务的数据传输并保留可继续下载所需的临时数据。
2. 当用户继续一个已暂停任务时，系统应在可恢复时从已有进度继续；如果服务器或资源状态不支持恢复，系统应清楚说明情况，并在重新从头下载前取得用户确认。
3. 当用户取消一个未完成任务时，系统应停止传输、清理该任务的未完成文件，并从下载列表移除该任务。
4. 当用户删除一个已完成任务的记录时，系统应询问是否同时删除对应文件；用户确认后，系统应只执行其选择的操作。
5. 当用户选择删除已完成文件时，系统应删除对应文件并移除相关完成记录；如果文件已不存在，系统仍应清除记录并给出适当反馈。

### 需求 3：后台下载与任务恢复

**用户故事：** 作为下载管理器用户，我希望在平台允许的后台状态下继续下载，并在应用或设备重启后找回任务，以便不因离开应用而丢失下载。

#### 验收标准

1. 当用户将应用切到后台或最小化时，系统应在所在平台允许的条件下继续活动下载；平台不允许持续执行时，应说明限制并保留可恢复记录，不应承诺进程退出、系统休眠或系统强制限制后仍能无限下载。
2. 当下载任务、缓存或设置发生变化时，系统应持久化这些数据，使其在应用重启后可恢复。
3. 当应用进程被终止或设备重启后，系统应恢复任务记录和已完成记录；Android、macOS、Windows 的未完成任务应保持待恢复状态，不应未经用户操作自动继续。iOS 允许已交由系统托管的后台任务继续，重新打开应用时应关联系统既有任务并同步实际状态，不重复提交；已失败、已取消或被用户强制退出后取消的任务应等待用户操作。设备重启后的 iOS 任务以系统查询结果为准，应用不得以恢复记录为由自行重新提交。
4. 当用户手动继续恢复后的未完成任务时，系统应尝试从已有进度继续；不支持续传时按需求 2 的验收标准处理。
5. 当所在平台的后台、通知或相关权限不可用时，系统应说明受影响的行为并提供可行的权限处理指引，不应静默丢失任务记录。

### 需求 4：管理已完成文件

**用户故事：** 作为下载管理器用户，我希望打开、重新下载或删除已完成的文件，以便管理下载结果。

#### 验收标准

1. 当用户打开已完成文件时，系统应调用所在平台可用的系统处理程序；平台不允许打开该文件或没有处理程序时，应明确提示。
2. 当 Android 用户打开 APK 文件时，系统应将文件交给 Android 系统安装流程处理，不应自行安装应用；macOS、Windows 和 iOS 不应把 APK 当作本平台可安装应用，也不应绕过所在平台的文件或安装限制。
3. 如果文件不存在或系统找不到可用的处理程序，系统应说明原因且不丢失其他任务记录。
4. 当用户选择重新下载已完成项时，系统应使用原下载链接创建新的下载任务，并保留原已完成文件。
5. 系统不应提供文件分享功能。

### 需求 5：保存和复用缓存配置

**用户故事：** 作为下载管理器用户，我希望保存常用的下载链接及其文件名和目录，以便之后快速重复下载。

#### 验收标准

1. 当用户新建缓存配置时，系统应要求下载链接，并允许用户填写可选文件名和可选保存目录。
2. 当用户保存缓存配置时，系统应保存该配置但不启动下载。
3. 当用户从缓存配置发起下载时，系统应创建新的下载任务并保留原缓存配置。
4. 当用户编辑缓存配置并保存时，系统应更新配置；取消编辑时，系统应保留原配置。
5. 当用户发起未指定独立目录的缓存下载时，系统应采用当时设置的全局默认目录。
6. 当用户删除缓存配置时，系统应只删除该配置，不应删除由其创建的下载任务或已下载文件。

### 需求 6：保存目录和文件命名

**用户故事：** 作为下载管理器用户，我希望为下载选择保存位置并避免覆盖已有文件，以便找到下载内容并保护已有文件。

#### 验收标准

1. 当任务或缓存配置指定了保存目录时，系统应优先使用该目录；未指定时，系统应使用全局默认目录。
2. 当用户在目录选择器中取消选择时，系统应保留此前的目录设置，不应将其清空。
3. 当用户更改全局默认目录时，尚未创建任务的缓存配置如果没有独立目录，应在之后启动下载时使用最新的默认目录。
4. 当下载任务已经创建时，系统应固定该任务的目标目录；后续修改全局默认目录不应改变现有任务的目标目录。
5. 当用户没有指定文件名时，系统应从下载响应或链接推导可用文件名；当推导失败时，系统应使用可识别的默认文件名。
6. 当目标目录已有同名文件时，系统应保留已有文件，并为新文件自动添加递增序号以避免覆盖。
7. 如果目录不可访问、授权失效或存储空间不足，系统应说明原因，不应报告下载成功。
8. 当用户尚未自定义全局默认目录时，Android 应使用系统公共 `Download/Downloader/`，macOS 和 Windows 应使用系统提供的当前用户下载目录下的 `Downloader` 子目录；目录不存在时应按需创建，首次下载不应要求用户先手动选择文件夹。iOS 应提供无需先选择目录即可使用的应用内持久保存位置，不假设存在可任意写入的公共 Download 目录；具体位置与文件访问方式在设计中验证并说明。

### 需求 7：配置主题和默认目录

**用户故事：** 作为下载管理器用户，我希望设置界面主题和默认保存目录，以便按个人偏好使用应用。

#### 验收标准

1. 当用户选择跟随系统、浅色或深色主题时，系统应按所选模式显示界面，并持久化该偏好。
2. 系统应允许用户在设置中更换全局默认保存目录；当用户完成平台允许的目录选择时，系统应持久化设置及必要的访问授权，并按需求 6 应用于未指定独立目录的新下载。
3. 当用户未授予所需目录访问权限时，系统应说明原因并允许用户重新选择目录。
4. 系统不应提供代理开关或代理配置。

### 需求 8：处理下载错误与重试

**用户故事：** 作为下载管理器用户，我希望了解下载失败的原因并能在问题解决后重试，以便恢复下载。

#### 验收标准

1. 当服务器拒绝请求、请求超时或网络断开时，系统应将任务标记为可识别的失败或等待状态，并说明原因。
2. 当用户修复网络或链接问题后选择重试时，系统应继续下载或按需求 2 的续传规则重新开始。
3. 当应用缺少存储或后台下载所需权限时，系统应说明所需权限及受影响的功能；用户拒绝权限时，系统应保持应用可用且不丢失已保存记录。
4. 当文件名、路径或存储空间导致下载无法完成时，系统应提示可采取的处理方式，并允许用户处理后重试。
5. 当下载失败或重试时，系统不应将不完整文件标记为已完成。

### 需求 9：易读且适配设备的界面

**用户故事：** 作为下载管理器用户，我希望在不同设备尺寸与系统显示设置下都能读取并操作下载列表，以便可靠地管理任务。

#### 验收标准

1. 当下载列表为空时，系统应显示明确的空状态和创建下载入口。
2. 当文件名或链接较长时，系统应以截断、换行或详情查看等方式呈现，不得覆盖进度、操作入口或其他列表内容。
3. 当键盘显示、系统字体放大或桌面窗口缩小时，新增下载、缓存新增及编辑界面的字段和操作仍应可见并可操作。
4. 当系统操作成功或失败时，系统应提供与结果相符的反馈。
5. 系统应提供中文界面，并使用 Flutter 及各平台标准无障碍语义支持屏幕阅读器、字体缩放和适用的键盘操作。

## 首期范围与约束

- 平台：Android、macOS、Windows 为必需；iOS 为希望同步提供、需验证可行性的平台。各平台最低系统版本和设备覆盖在设计阶段确认；iOS 系统托管后台任务例外按需求 3 执行。
- 协议：普通 HTTP/HTTPS 及重定向；不含认证资源、磁力链接和视频解析。
- 不包含：应用内代理、文件分享、搜索、批量管理及其他语言。
- 成功标准：用户能够创建 HTTP/HTTPS 下载，观察任务进度，暂停并继续；后台行为符合各平台规则；记录可恢复，Android/macOS/Windows 的未完成任务由用户手动继续，iOS 关联系统托管任务且不重复提交失败或取消任务；缓存配置可重复使用；文件可按规则保存、打开和删除，异常时不会静默丢失记录或覆盖既有文件。
